# Tutti opinionated scaffold: Python vertical via create-from-scratch

Status: proposed
Date: 2026-08-14

## Goal

Turn Tutti from a workflow driver into an **opinionated engine**: when it creates a
repo, it imposes a known-good, agent-friendly shape (structure, real CI, formatters and
linters as gates, a single canonical gate command, `AGENTS.md`), the way Black imposes a
formatting style. The payoff is measurable: an autonomous agent working in a Tutti repo
should hit a green CI gate on the first try, with few review/fix cycles.

This spec covers the **first slice only**: the profile mechanism, the scaffold emitter,
one reference profile (**Python**), and its wiring through the existing
create-from-scratch flow (#19). Rust/TS/Go profiles and the retrofit flow (#16) are
explicit follow-ups (see Out of scope).

## Decisions (settled)

- **First slice:** a single Python vertical, end to end through create-from-scratch, so
  a new repo lands Tutti-ready with real CI, a real gate, and `AGENTS.md`. Proves the
  whole mechanism on the thinnest path.
- **Opinions are declarative data**, not imperative code: each language is a
  `StackProfile` value (files + gate command + CI). Fixed and opinionated (no user
  overrides in this slice), unit-testable against golden output, and adding a language is
  adding data.

## The opinion: the Python stack

Research-backed (see the shakeout research; sources omitted here for brevity). One
coherent stack, tuned so an agent's local pass predicts CI:

| Concern | Choice |
|---|---|
| Env + packages | **uv**, committed `uv.lock`, `uv sync --frozen` in CI |
| Format + lint | **ruff** (`ruff format --check` + `ruff check`), pinned |
| Type check | **mypy `--strict`** on `src` |
| Tests + layout | **pytest**, `src/` layout, `tests/` mirroring it |
| Interpreter pin | `.python-version` |
| Canonical gate | `scripts/check.sh` (one command; CI and the agent both run it) |
| CI | GitHub Actions: setup-uv, then `bash scripts/check.sh` |
| Agent contract | `AGENTS.md` naming the gate + conventions |

The canonical-gate entry point is deliberately `scripts/check.sh` for *every* language, so
`tutti.toml`'s `[gate]` is always `["bash scripts/check.sh"]` regardless of stack. Future
profiles emit their own `scripts/check.sh`.

### Emitted file set (Python profile)

```
<repo>/
├── AGENTS.md                    # names the gate + conventions (agent contract)
├── scripts/check.sh             # the one canonical gate (chmod +x)
├── .github/workflows/ci.yml     # setup-uv -> bash scripts/check.sh
├── .python-version              # pins the interpreter
├── .gitignore                   # py caches, .venv, ruff/mypy caches
├── pyproject.toml               # uv + [tool.ruff] [tool.mypy] [tool.pytest.ini_options]
├── uv.lock                      # committed (generated at scaffold time, see below)
├── src/<pkg>/__init__.py
├── src/<pkg>/core.py            # one tiny placeholder function
└── tests/test_core.py           # a passing placeholder test
```

`<pkg>` is the repo name normalized to a valid Python identifier (lowercased,
non-alphanumeric to `_`, leading digit prefixed with `_`). The placeholder function +
test guarantee the scaffold is **green on first CI run** (an agent-friendliness
requirement: never hand the agent a red baseline).

`uv.lock` is generated by running `uv lock` in the scaffolded dir at emit time (the one
place the emitter shells out). If `uv` is absent, the lock is skipped and CI falls back to
`uv sync` (non-frozen) with a recorded warning, rather than failing the scaffold.

## Architecture

Four small, independently testable units.

### 1. `StackProfile` (data model) — `tutti-app-core/src/scaffold.rs`

```rust
pub struct StackProfile {
    pub id: &'static str,               // "python"
    pub display_name: &'static str,     // "Python"
    /// Files to write, relative to the repo root. Order-independent.
    pub files: fn(ctx: &ScaffoldContext) -> Vec<ScaffoldFile>,
    /// The canonical gate written into tutti.toml's [gate].
    pub gate_commands: Vec<String>,     // ["bash scripts/check.sh"]
    /// A shell-out run after files are written (e.g. `uv lock`); best-effort.
    pub post_write: Option<PostWriteStep>,
}

pub struct ScaffoldFile { pub path: PathBuf, pub contents: String, pub executable: bool }
pub struct ScaffoldContext { pub repo_name: String, pub package_name: String }
```

The Python profile is one `StackProfile` value (built by `fn python_profile() -> StackProfile`,
since the owned fields are not `const`-constructible). `files` is a function of the context so
`<pkg>` and the repo name flow into `pyproject.toml`, `AGENTS.md`, and the package path.
Rendering is plain string formatting (no template engine): the contents are known-good and
diff-reviewable.

### 2. The emitter — `scaffold(dir, profile, ctx) -> ScaffoldReport`

- Writes each `ScaffoldFile` under `dir`, creating parent dirs, setting the executable bit
  where asked.
- **No-clobber:** if a target file already exists, it is **skipped** and recorded in the
  report (never overwritten). This keeps the emitter safe if create's auto-init README or a
  `.gitignore` is already present, and makes it reusable by the retrofit slice later.
- Runs `post_write` best-effort; a failure is recorded, not fatal.
- Returns `ScaffoldReport { written: Vec<PathBuf>, skipped: Vec<PathBuf>, warnings: Vec<String> }`.
- Pure enough to unit-test against a `tempfile::TempDir`; the only side effects are the
  filesystem and the one `post_write` shell-out (injected behind a seam for tests).

### 3. Branch + config seeding (the `init_project` seam)

Wiring changes at the mapped seams (all in `tutti-app`):

- **`InitParams` / `render_tutti_toml`** (`tutti-app-core/src/lib.rs`): `InitParams` gains
  `stack: Option<StackId>`. When a stack is chosen, `gate_commands` come from the profile
  (real gate), not the no-op `["true"]`. When no stack is chosen (retrofit/none), behavior
  is unchanged.
- **`init_project`** (`tutti-app/src-tauri/src/commands.rs`): after writing `tutti.toml`
  and before/with `seed_status_labels`, when a stack is set:
  1. `scaffold(form.dir, profile, ctx)` writes the files.
  2. Commit the scaffold on the default branch and push.
  3. **Seed the integration branch**: create `staging` (config's `integration_branch`)
     from the default branch and push it. This closes the app-map gap that onboarding
     never creates `staging`, so the engine's first drain has a real target.
- **Wizard** (`tutti-app/src/lib/wizard.ts`): add a `"stack"` `StepId` after `"repo"`.
  A single-select list of available stacks plus "None (I'll wire it myself)". The choice
  threads `WizardState -> toInitForm -> InitForm -> params_from -> InitParams.stack`.

### 4. Stack registry

`fn available_stacks() -> &'static [StackProfile]` returns the built-in profiles. This
slice ships exactly one (`python`). The wizard renders rows from it; adding a language is
adding a `StackProfile` to this list.

## Data flow (create-from-scratch, with a stack)

1. Wizard: forge -> namespace -> details -> **stack (python)** -> destination -> review.
2. `create_repo` (existing) creates the forge repo (auto-init README) and `clone_repo`
   clones it.
3. `init_project`:
   - writes `tutti.toml` with the profile's real gate,
   - `scaffold(...)` emits the Python files (README already present -> skipped, recorded),
   - commits + pushes the scaffold on the default branch,
   - creates + pushes `staging`,
   - seeds `status:*` labels (existing).
4. Result: a repo whose first CI run is green, with a real gate, `AGENTS.md`, and a
   `staging` target ready for the engine.

## Error handling

- **No-clobber** protects any pre-existing file (README, `.gitignore`); those are skipped
  and surfaced in the report, never overwritten.
- **`uv lock` absence or failure** is a recorded warning, not a scaffold failure; CI's
  non-frozen fallback keeps the repo buildable.
- **Branch seeding failure** (e.g. `staging` already exists) is idempotent: creating an
  existing branch is a no-op, mirroring `seed_status_labels`' best-effort shape.
- If `scaffold` fails before any push, `init_project` unwinds the `tutti.toml` it wrote
  (existing behavior already deletes `tutti.toml` on activation failure).

## Testing

- **Golden-file test** (unit, `tutti-app-core`): emit the Python profile into a `TempDir`
  and assert the exact file set and that key files contain the pinned tools (`uv`, `ruff`,
  `mypy` strict, `pytest`) and the canonical gate. The sandbox's `py/` subtree is the
  reference the golden output is derived from.
- **No-clobber test:** pre-create `README.md` and `.gitignore`, scaffold, assert they are
  in `skipped` and untouched.
- **`ScaffoldContext` naming test:** repo names like `My-Repo 2` -> package `my_repo_2`.
- **Wizard step (pure):** the `"stack"` `StepId` state machine and `toInitForm` mapping,
  over fakes (matches the existing `wizard.ts` test style).
- **`render_tutti_toml`:** with a stack set, the emitted `[gate]` is the real gate, not
  `["true"]`; with no stack, unchanged.
- Live checks (a scaffolded repo's CI actually passing on GitHub) are `test:manual`
  against a throwaway repo, out of the required gate.

## Out of scope (explicit follow-ups)

- **Rust / TypeScript / Go profiles** — pure data additions to the registry once the
  mechanism lands (each is a `StackProfile` matching the sandbox's `rs/` `ts/` `go/`).
- **Retrofit / tutti-fy (#16)** — detect existing language(s) and add only the missing
  tooling to an existing repo without clobbering. Reuses the same emitter (its no-clobber
  is designed for this) but needs language detection and a different UX.
- **User-overridable profiles/templates** — deliberately excluded; the thesis is one
  opinionated way. An escape hatch can come later.
- **A polyglot repo from create** — the create flow scaffolds one stack; multi-stack
  monorepos (like the sandbox) are not a create target yet.
